# Orua v5.1 设计规格：实机可用性修复

> 本规格在 v5（2026-11-07-orua-v5-design.md）之上增量演进，v1–v5 全部功能与测试保持有效。
> v5.1 是 **v5.0 实机验收后的缺陷修复版**，不含新功能。它修的是一个从 v1 潜伏至今、**所有自动化测试都没抓到**的致命 bug。

## 1. 背景

v5.0 完成后做真实 GUI 验收，界面显示「后端已连接」，但发送消息只得到 `Failed to fetch`，聊天完全不可用。后端日志显示**聊天请求从未到达后端**。

## 2. 根因

### 2.1 聊天请求漏拼 `API_BASE`

前端 `consumeSse()` 的实现：

```js
// 错误（v1 – v5.0）
async function consumeSse(url, body, handlers) {
  const res = await fetch(url, { ... });   // 裸相对路径
}
// 调用处
await consumeSse('/api/v1/chat/stream', { ... });
```

页面由 WebView2 通过 `SetVirtualHostNameToFolderMapping` 以虚拟主机 `https://app.local` 提供，因此相对路径 `/api/v1/chat/stream` 被解析为：

```
https://app.local/api/v1/chat/stream   ← 虚拟主机目录里没有这个文件
→ net::ERR_FILE_NOT_FOUND
→ 浏览器抛 TypeError，前端 catch 后显示 "Failed to fetch"
```

对照组：`App.api.req()` 一直是正确的：

```js
const res = await fetch(API_BASE + path, opts);   // 正确
```

**5 处 `fetch` 里只有 `consumeSse` 漏拼**，而它恰好承载单聊与重新生成两条主链路。

### 2.2 为什么长期没被发现

| 测试手段 | 为什么漏掉 |
|---|---|
| 三个 stub 闸门（109/54/19 条） | 用相对路径 stub 替换 `fetch`，不经过真实网络栈 |
| `test_api.ps1` | 用 curl 直打 `http://127.0.0.1:8765`，绕过了前端 |
| `smoke_gui.mjs`（v5.0 版） | 只在控制台里 `fetch(API_BASE + ...)` 验证令牌，**从未点过「发送」按钮** |
| ctest | 纯后端，不涉及前端 |

结论：**所有测试都在「绕过前端页面」的层面验证，没有一条走过「真实页面里点按钮」的完整路径。**

### 2.3 `build_backend.cmd` 中文路径误报

VS 安装在 `D:\Ruanjian\VS\本体`，`vswhere.exe` 按 UTF-8 输出该路径，而 cmd 默认代码页（936）将其转成乱码 `D:\Ruanjian\VS\����`，`if not exist "%CMAKEEXE%"` 判定失败 → 误报 `[ERROR] cmake not found`，`publish.cmd` 无法一键构建。

## 3. 修复

### 3.1 `consumeSse` 拼接 `API_BASE`

```js
// 正确（v5.1）
async function consumeSse(path, body, handlers) {
  const res = await fetch(API_BASE + path, { ... });
}
```

参数名由 `url` 改为 `path`，明确它现在是**相对路径**，防止后续维护者误传绝对 URL。

### 3.2 构建脚本切 UTF-8 代码页

`scripts/build_backend.cmd` 开头加 `chcp 65001 >nul`，使 `for /f` 从 `vswhere` 读到的路径与磁盘真实路径一致。

### 3.3 把「真实点击发送」固化成断言

`scripts/smoke_gui.mjs` 新增第 6 步：填入文本 → 点击「发送」→ 等 5 秒 → 断言聊天区**不含** `Failed to fetch`。

这是本规格的核心产出：**测试必须覆盖「真实页面点按钮」这一层**，否则同类 bug 还会潜伏。

### 3.4 版本号 5.1.0

三处同源：csproj `<Version>5.1.0</Version>`、`/health` `5.1.0`、`index.html` 脚注 `v5.1`。

## 4. 验收标准

1. 真实 WebView2 中点击「发送」：请求为 `http://127.0.0.1:<port>/api/v1/chat/stream`，收到 AI 回复，无 `Failed to fetch`。
2. 「重新生成」同样可用（共用 `consumeSse`）。
3. 全部 5 处 `fetch` 均以 `API_BASE` 开头，无裸相对路径。
4. `build_backend.cmd` 在中文路径 VS 下能找到 cmake/ctest；`publish.cmd` 一键跑通。
5. `dist\Orua\AiCompanion.exe` 文件版本 `5.1.0.0`、产品名 `Orua`；`/health` 为 `5.1.0`；脚注 `v5.1`。
6. `smoke_gui.mjs` 支持 `CDP_PORT` 环境变量。
7. v1–v5.0 全部自动化测试保持全绿。

## 5. 已知非缺陷

- **头像 `ERR_BLOCKED_BY_ORB`**：Bot 未上传头像时 `/api/v1/bots/{id}/avatar` 返回 404 空响应，浏览器对 `<img>` 的 404 做 ORB 拦截属正常行为，前端回退默认 emoji 头像。不影响任何功能。

## 6. 教训

**「后端 API 通了」≠「应用可用」。** 凡是「用户点击 → 前端发请求 → 后端响应 → 界面渲染」的链路，验证必须从**用户动作**这一端发起。用 curl 验证后端、用 stub 验证前端逻辑，两者都对，合起来仍可能整条链路是断的。
